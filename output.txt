RecursiveCharacterTextSplitter             300       50       34
CharacterTextSplitter                      300       50       24

RecursiveCharacterTextSplitter: longest chunk = 299 | chunks bigger than chunk_size = 0
CharacterTextSplitter:          longest chunk = 457 | chunks bigger than chunk_size = 10

Explanation:
RecursiveCharacterTextSplitter can use several separators (paragraph,
line, word), so it always finds a place to cut and every chunk stays
inside the chunk size. CharacterTextSplitter only looks for one
separator (\n\n). If no blank line exists inside the chunk size it
cannot cut the text, so the chunk becomes bigger than chunk_size.
(LangChain even printed warnings like 'Created a chunk of size 455,
which is longer than the specified 300'.)
This is why the recursive splitter is usually the better choice.

OBSERVATIONS
==================================================
1. Chunk size experiment:
   chunk_size =  200, overlap =  20  ->   41 chunks
   chunk_size =  500, overlap =  50  ->   12 chunks
   chunk_size = 1000, overlap = 100  ->    6 chunks
   chunk_size = 100, overlap = 0     -> 63 chunks
   chunk_size = 5000, overlap = 0    -> 1 chunks
   A bigger chunk size means fewer chunks.

2. Chunk overlap experiment (chunk size = 300):
   overlap =   0  ->   34 chunks, repeated text in  0 of 33 chunk pairs
   overlap =  50  ->   34 chunks, repeated text in 10 of 33 chunk pairs
   overlap = 100  ->   34 chunks, repeated text in 10 of 33 chunk pairs
   overlap = 200  ->   38 chunks, repeated text in 14 of 37 chunk pairs
   A bigger overlap means more repeated text, and a little more chunks.
   The repeated text keeps a sentence understandable in both chunks,
   but it also uses more space.

3. Splitters: the recursive splitter always stayed inside the chunk
   size, the character splitter produced chunks bigger than chunk_size.
   Both splitters kept the metadata of the original document.
